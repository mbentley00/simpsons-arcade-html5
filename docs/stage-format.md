# Stage backgrounds and editor

Open `web/editor.html` through the same HTTP server as the game. It uses the ROM picker and IndexedDB cache from `romload.js`. Select a stage, section, and background layer, then select a block and paint. Right-click or Alt-click samples a block. Undo and redo apply to each paint stroke. Export saves changed program-ROM bytes as JSON; import replaces the current edits. No ROM images are included in this repository.

Edits are stored under `simpsons.stagepatch.v1` in localStorage for this origin. The game reads them on page load. **Play this stage** saves first and opens `index.html?scene=N&play=1`, automatically starting the player and skipping the visible introductions. The first launch prepares the native game in the background. A ready-to-play checkpoint is stored privately in IndexedDB for subsequent launches of the same stage and edits. The key includes the scene, edits, initial EEPROM, build and launch-code version. Checkpoints are generated from the user's ROM at runtime and are never included in the downloadable code package. `&fresh=1` bypasses a cached launch. Without `&play=1`, `?scene=N` retains manual coin/start behavior. Reload the game after further edits. `?mods=0` disables edits and scene selection. Invite links containing `?sala=` also disable them. A locally modified game cannot create or join a room through the panel; open a fresh game with `?mods=0` first.

Background mode changes the two scrolling background maps. Replacing a background block does not change where the player can walk. Some screens and block sets are shared, so one edit may appear in several places. The other layer is faded for reference rather than composited exactly as in gameplay. Palette animation and scene-specific effects are not simulated.

## Enemy placement

Select **Enemies**, choose Rivet, Duffman or Standard enemy, and click empty map space to add a spawn. The preview updates to the selected custom character. Drag the ellipse at an enemy's feet to move it, or select it and enter X/Y coordinates. Delete selected, the Delete key, or right-click on the marker removes it. Undo/redo includes enemy changes. Every record in the stage's spawn stream is shown. Basic enemies (ids 0–4) and the stage's own objects are drawn with their in-game sprites. `tools/capture_native_sprites.js` plays each stage and catches every spawn at the allocator (pc 0xCA80; characters go to RAM 0xF80+, props to 0x1280+, flag-12 records to one controller slot at 0x1640). To find an object's sprite entries, it reruns the same frame with the object moved 1024 px and keeps the entries that differ. It also adds nearby entries that use the object's palette and sit closer to it than to anything else. `web/stage/native_sprites.js` stores only the K053247 entries, colour base, K053246 offsets, feet anchor and prog.bin offsets of the palettes. The editor renders the picture from the user's sprite ROM and prog.bin, so no graphics or colours are shipped. Captures are keyed `stage:id` because ids are reused (0x0C is a door in the street and a goon in the park), and names are in `web/stage/native_names.js`. The current capture covers 48 objects in eight combat stages; the power plant, Stage 4 part 1 and the dream have none, and objects that never appeared on screen during the capture runs show as boxes. Characters and props are movable and placeable: **Place** copies the stage's first record of that id with a new X/Y. Scripts and triggers (flag 12, or ids 0xE0 and above) are grey and read-only. Two are identified (0xE9 in the street is the police car arriving at the fire station; 0xEB is a goon entrance). Flag-12 records are labelled "Stage trigger": they allocate a controller object, but the camera stalls did not line up with their X positions consistently, so their exact role (wave or scroll control) is not decoded. **Duplicate group to X** copies the selected record and every record within 40 px of it, changing only X; edited rows, including copied scripts, are re-inserted by X. Copied events depend on scenery they may expect (for example fixed-layer fence tiles), so treat that as experimental. Export/import includes enemy changes and custom skin IDs. The JSON references bundled custom art, rather than copying ROM graphics into an exported file.

Enemy positions are spawn-stream coordinates: horizontal world X and depth in eight-pixel units. The game spawns enemies ahead of the camera; they may walk onto the screen from an edge. Map markers are authoring coordinates, not exact on-screen spawn positions. Placements apply to the whole stage's spawn stream; use the Main section for placement. Enemy placement is disabled for bonus rounds and the ending. Scripted encounters and transitions keep their original game rules. The scene-to-stream mapping comes from the ROM's table at 0xe88d, read at 0xba87; cemetery, dream and power-plant intros lead to their subsequent combat scenes.

`web/stage/enemies.js` reads the spawn-table index at fixed CPU address 0xefbc. Each entry points into bank 0x1b to a word containing the spawn-stream pointer. Each record is eight bytes: big-endian X, signed depth divided by eight, height, allocation flags, variant, minimum-player gate, and object/script ID. FF in the first byte terminates the stream. Unedited records retain their exact order, including intentionally non-monotonic coordinates. Added and moved basic enemies are inserted by X without reordering other scripts or props.

Offline game hooks expose the edited stream through a virtual bank-0x1b window at 0x7800–0x7fff. The original program image and its boot checksum stay intact. Lists are limited to 255 records plus the terminator. Custom skins are tagged when the original allocator completes at 0xca80; the native enemy object, AI, attacks, damage, collision and death handling remain in control. Enemy mods are disabled on invite links and with `?mods=0`, and they block online room creation/joining from a modified offline page.

## Duffman sprite asset

`web/custom/duffman.js` contains custom artwork only. It stores sixteen 64×96 frames as 384 tiles (16×16 pixels, 128 bytes each), using the K053247 four-bit nibble ordering decoded by the game. Each sprite has fifteen visible colours plus transparent pen zero. Its 32-byte palette uses the board's big-endian RGB555 words. Storage anchor is (32, 91). The editor and game share `displayScale: 0.75`: a 48×72 display frame with anchor (24, 68), sampled with nearest-neighbour pixels. The visible standing character is about 57–60 game pixels tall. Mirrored poses are rendered at runtime. The animation groups are idle, walk, arm/punch gesture, recoil, and fall. Display poses follow the native enemy's movement/state; this is a custom skin, not a new combat AI or ROM animation program.

The renderer substitutes the custom frame for that enemy's native sprite pieces, preserving tile-layer and sprite priorities. The palette is private to the renderer and does not overwrite the game's palette RAM. `tools/build_duffman.py` converts the source atlas into the packed JS asset, `.4bpp` tile data, `.pal` palette and PNG preview. These are native-format graphics exports; they are not a drop-in standalone MAME ROM patch.

## Rivet and multiple custom characters

Rivet is an original maintenance goon with a navy cap, orange vest, teal coveralls and cream gloves. `web/custom/rivet.js` uses the same 16-frame, 4bpp tile format, 16-entry RGB555 palette and 48×72 display size as Duffman. Each asset registers in `window.SIMPENEMY_ASSETS`. Editor thumbnails and labels come from the selected asset. Rivet uses the original basic enemy's AI and collisions; the custom idle/walk/attack/recoil/fall frames provide his appearance.

The game keeps a separate private presentation palette for each custom character. It stores the skin ID with the native actor and DMA record, so Rivet and Duffman can appear together and survive save/load or direct-launch checkpoint restoration. Native palette RAM remains unchanged. The direct-launch cache signature includes hashes of custom tile data, palettes and display scale, plus the launch-code version, to prevent restoring obsolete skin data after artwork changes.

The converter also supports other asset IDs and palettes: `python tools/build_duffman.py SOURCE.png OUTPUT --id rivet --name Rivet --colors HEX,HEX,...` (sixteen RGB entries, including transparent pen zero). The historical filename remains compatible with Duffman exports.

Slugger (`web/custom/slugger.js`) is an original man in an oversized white baseball costume with red seams, a navy cap and red shoes. His tile/palette/frame format matches Rivet and Duffman. Downed poses play once and hold the final frame instead of cycling backward; landing gets a short hold to avoid pose flicker. The Duffman last-row source poses were separated into complete connected silhouettes and repacked after neighboring cells were found to contain clipped limbs/fragments. The first twelve packed frames remain byte-for-byte unchanged. `tools/repack_sprite_cells.py` performs this source-cell repair without drawing new artwork.

Hans Moleman (`web/custom/moleman.js`) is a hunched old man with a bald yellow head, huge round glasses, white shirt, peach tie, high-waisted green trousers and a wooden cane. `tools/build_moleman.py` draws his sixteen frames procedurally (idle with a shaking fist, shuffling walk, an overhead cane swing and jab, recoil, falling back and lying down); `tools/build_duffman.py ... --id moleman --name "Hans Moleman" --colors ...` packs them in the same 4bpp format. He uses the standard enemy's AI like the other custom characters.

Comic Book Guy (`web/custom/comic_book_guy.js`) is a very large man with a brown ponytail, small glasses, a stubbly double chin, a light-blue T-shirt stretched over his belly, khaki shorts, white socks and dark shoes. `tools/build_comic_book_guy.py` draws him part by part at 4x size and poses sixteen frames (idle breathing with a blink, a waddling walk, pulling a rolled-up comic back over his head and swatting with it, recoil, tipping over and lying flat); the frames are reduced to the 64x96 cell with 1 px ink outlines between parts and packed by `tools/build_duffman.py`. He uses the standard enemy's AI. Custom palettes get 16-pen slots from 4096 in sorted asset-id order, so tests look slots up by id.

## Friendly NPCs

The **NPCs** tool saves a custom character row with `role: "npc"`, `npcName` (up to 40 characters) and `dialogue` (up to 200). It uses the same world coordinates, history and JSON export as enemy placement. NPC rows are removed from the virtual combat spawn stream entirely. They render as idle custom characters using camera-relative positions and private palettes, without allocating native enemy objects, hitboxes or wave counters. Blue labels identify them. `web/stage/npc.js` shows a proximity prompt and pauses the game for dialogue on E. Closing the dialogue restores gameplay. Bonus rounds and the ending retain their existing editor restrictions.

## Arcade Remix implementation

`web/combat.js` wraps native RAM writes to object health at +0x1b and identifies the attacker from the CPU's X/U object registers. The observed native damage stores complete at fixed PCs 0xc280 and 0xc2b6; the module follows actual health reductions rather than counting button presses. The original CPU still runs collisions, AI, reactions and object lifetime. Confirmed hits build a chain and focus; every third hit adds finisher damage. Up+Attack sets a launcher intent, and a landed launcher adds native Z position/velocity at +0x16/+0x19. Air hits receive a damage bonus. Dodge raises native X velocity briefly while filtering incoming damage/stagger writes. Movement upgrades scale velocity when the native code assigns it. Focus Burst spends meter and applies damage/reaction/knockback only to nearby native enemy actors. NPCs have no such actors and are unaffected.

Basic native enemies are raised to a stage-scaled minimum health (12 at stage 1, capped at 32) so that confirmed-hit chains and juggling have room to work. The run's maximum health is held in mod state; unrelated native object fields are not used as a maximum-health variable. Upgrades are run-scoped plain board data. A forward scene transition from a completed combat stage opens three distinct seeded choices at the next safe frame boundary. Stage 4 part 1 and bonus-round exits are excluded; the final power-plant exit marks a win. Selecting a card applies the upgrade and releases the hold on the native game. Returning to attract/title resets the run. Keyboard and gamepad shortcuts are suppressed in text fields and dialogue/draft UI.

A player damage write that the dodge filter cancels is a perfect dodge: once per dodge it sets a 60-frame counter window (more with Riposte) in which landed hits are multiplied by 1.5. Momentum, Juggler, Shockwave and Overcharge modify the same confirmed-hit, launcher-effect and Focus Burst paths; Shockwave applies the Focus Burst reaction fields to other basic enemies near a finisher target without extending the combo. Elites are rolled from the seeded run RNG when a basic enemy is first seen (stage 2 onward, 8% + 4% per stage), raising its native health by 60% (cap 56); there is no new enemy object or AI. Per-stage stats (start frame, damage taken, best combo, KOs, elites, counters) are plain run data and give the results-card rank. Drafts pick without replacement with weights common 6, rare 3, epic 2. Hit-stop is presentation only: a 45–90 ms wall-clock hold reported through `SIMPCOMBAT.blocked`, during which game.js skips frames; it is not board state and is disabled with reduced motion or in Node checks.

Bowling balls (B / gamepad button 7, RT) are plain board data in `arcadeCombat.balls`: thrower, world x (object x + camera word 0x8ac), depth (object +0x11), direction, birth frame, colour and the slots already hit. A throw needs no meter and has a 20-frame cooldown. Each frame before the native step, a ball advances 5 px. It hits every live, non-invulnerable native enemy within 14 px horizontally and 12 px of depth, once per enemy, for 6 damage (scaled by Heavy hands). The hit is written the way the game's own attacks write it: hit kind at +0x1e, health at +0x1b, attacker pointer at +0x25, then flag 0x20, and the enemy's handler plays the reaction on the next frame. Kinds confirmed from native attacks: on enemies 0x11/0x12 flinch and 0x14 knocks into the air and down; on players 1 flinches and 2 knocks down. Any other kind is ignored: an early build wrote 3, so balls, Focus Burst and Shockwave took health without any reaction. Balls and Focus Burst use 0x14, Shockwave 0x12. A ball hit counts as a confirmed hit. A ball that hits three enemies triggers STRIKE!. Balls expire after 110 frames or off screen, and are cleared outside combat stages. The overlay draws them (ball, spin holes, hop, shadow) from that data only.

The Remix UI is drawn into the finished frame. game.js keeps the clean game frame (`SIMPG.pixels()` and the frame hash read it) and, on every display frame, copies it and calls `SIMPCOMBAT.drawOverlay`. That draws the player strips, callouts, the screen shake, the results/draft screen and the H how-to-play page with a built-in 3×5 pixel font. Because it redraws each display frame, the draft and help screens animate while the board is held. `SIMPG.screenPixels()` returns the composed picture. Draft input uses the local keys (arrows/WASD, Z/J/Enter/Space, 1–4) and gamepads, which are polled from the overlay, and mouse clicks mapped through `#screen`'s on-page rectangle. Game input is blocked (`SSRIN.block`) while the draft or help page is open. A visually hidden `#combat-live` region reads the results and choices to screen readers. No Remix HTML panels remain; the page's Pause/Mute buttons are separate page controls.

Combat is installed after direct-launch preparation, so each editor launch begins a fresh run. It is disabled by `?combat=0`, `?mods=0` or an invite link. Online room creation/joining requires unmodified behavior. This is an offline gameplay remix, not a native ROM patch or a port of another game's code.

## Custom stages

`web/stage/stages.js` (SIMPCUSTOM). The editor document holds

    stages: { "<id>": { name, scene, tileset: {id, maps: [back, front]} | null, enemies: [spawn rows] | null, events: [{type, x}] } }

`scene` is the original stage whose ground is used (its ROM maps, collision, section scripts and timing). `tileset` is its level art, which must belong to that scene. `enemies` replaces that stage's spawn list for this stage only (null = the original list). `events` are scripted events for its art. Ids are lower-case slugs; there are at most 16 stages. `index.html?custom=<id>&play=1` warps to the base scene and installs the art, enemies and events; without `?custom` no custom art or events are installed and the originals run as they are, while global byte and enemy edits still apply. The launch checkpoint signature includes the custom id. Documents with the older `tilesets: {scene: {id, maps}}` overrides are migrated (in the editor, the game and imports) to one custom stage per entry, named after the art.

## Scripted events

`web/stage/events.js` (SIMPEVENTS). Each event is `{type, x}`; it fires once, when `camera + 160 >= x` while the custom art's stage value and section are loaded. Run state is plain data in `m.stageEvents` (`fired`, `live`, a xorshift seed, the banner). `beforeFrame` runs before each native frame and `drawOverlay` draws into the finished frame under the Remix HUD. Hits use the native hit write (see bowling balls above).

Bowling Alley types:

- `ball`: a 45-frame flashing warning at the screen edge on a random player's depth lane, then a 13-px-radius ball rolls 5 px per frame; players within 19 px and 10 depth are knocked down (kind 2, −5 health, never below 1; airborne or dodging players are missed) and enemies are knocked down (kind 0x14, −10). Odd-numbered events roll from the left.
- `pins`: for 300 frames a pin falls every 15 frames near a player (±64 px, ±12 depth) for 34 frames with a growing shadow; on landing it flinches players (kind 1, −3) and enemies (kind 0x12, −5) within 11 px / 9 depth.
- `cosmic`: 720 frames of blacklight recolouring of the custom pens (0x2000–0x21ff) with a flicker on and off; the normal colours are restored afterwards.
- `frenzy`: 600 frames in which each player's bowling-ball cooldown is capped at 5 frames (needs the Remix).

## Events from a description

`web/stage/recipes.js` (SIMPRECIPE). A described event is stored as `{type: "custom", x, prompt, recipe}` and is allowed in any custom stage; without level art the events run while the base stage's stage value is loaded (any section). A recipe is data, never code:

    recipe = { name, banner, color, summary, actions: [ { kind, delay, duration, object, from, target, effect, damage, count, speed, size, tint, amount, text } ] }

`normalize()` clamps everything (at most 6 actions; delay 0–30 s; duration 0.5–30 s; damage 0–20; count 1–12; amount 0–40; text 24 characters; unknown kinds dropped, unknown enum values replaced), on every load and on every answer from Claude. Kinds:

- `projectile`: `count` objects spread over `duration`, each aimed at a random target's depth lane with a 36-frame warning arrow, moving 3/5/8 px per frame (`speed`) with radius 7/11/16 (`size`); hits like the runaway ball (airborne and dodging players are missed). `from` left, right or both (alternating).
- `rain`: for `duration`, `count` objects per second fall near random targets (±64 px, ±12 depth) over 34 frames and hit what is under them on landing.
- `blast`: hits every target on screen at once (dodging players are missed) and draws a ring.
- `tint`: recolours the finished frame for `duration` (night, blacklight, red, green, sepia, invert, flash); night and blacklight flicker on and off. Drawn before the objects and under the Remix HUD.
- `shake`: offsets the finished frame by up to `amount` (1–6) px each frame for `duration`.
- `heal`: adds `amount` health, capped at the Remix maximum or, without the Remix, the highest health seen for that player.
- `frenzy`, `banner`: as the bowling `frenzy`; `text` shown as the banner.

`target` (players, enemies, everyone) chooses both what is aimed at and what can be hit. `effect` flinch writes kind 1 to players / 0x12 to enemies, knockdown kind 2 / 0x14; players never go below 1 health from an event.

Recipes come from `generate(prompt, key)`: the editor loads `@anthropic-ai/sdk@1.3.0` from jsDelivr and calls `claude-opus-5-5` from the browser (`dangerouslyAllowBrowser`, the designer's own key, stored only in their localStorage) with a system prompt describing the blocks and `output_config.format` set to the recipe's JSON schema, effort medium, and `fallbacks: "default"` (retried without it if the API rejects the field). A refusal or a cut-off answer is reported; on any failure the editor falls back to `fromText()`, a keyword reader for common words (rain/fall, roll/fly/charge, explosion/earthquake, lights out, neon, alarm, toxic, shake, heal, frenzy; donuts, boulders, fire, Duff, bombs, pies, anvils, pins, balls; giant/small, fast/slow, from the left, only the enemies, knock down; "8 seconds", "five").

## Custom level art: Springfield Elementary

`web/custom/tileset_school.js` is an original background tileset generated by `tools/build_tileset_school.py` (procedural pixel art at native resolution, no ROM data). It has two parts: a schoolyard (welcome sign, two-storey brick school with the name over the entrance, clock and bell tower, school bus, gym, fence, hopscotch and four-square on the blacktop) and an indoor hallway (lockers, classroom doors, bulletin board, drinking fountain, trophy case, checkered floor). It uses 74 colours and 280 back + 214 front 32×32 blocks, zlib-compressed. Re-run the tool after changing the drawing code; `--preview DIR` writes PNGs.

In the editor, choose **+ New stage…** and start from Springfield Elementary. Only the picture differs from Stage 1: its ROM maps, and therefore its collision and walkable ground, stay exactly as they are, together with its enemies, scripts and timing. The block picker lists the school blocks, and painting edits the stage's own maps (56×8 block ids per layer). The Stage 1 street itself is unchanged.

How it works (`web/stage/tileset.js`): the K052109 tile ROM is full (all 32,768 codes are used), so new art cannot be added as tiles. Changing the ROM maps is not an option either: the game derives collision from the map's block numbers (an early build did this and froze the players and enemies). Instead, while stage value 0x82 section 0 is loaded, every pixel of the two scrolling layers is taken from the custom maps by world position, with a private palette (pens 0x2000–0x20ff, shadowed copies at 0x2100). In Stage 1 both scroll registers are always the camera word at RAM 0x8ac plus 422, modulo 512; the camera resolves the 512-pixel wrap, and ±3 px of screen shake is tolerated. The fixed layer (HUD, plus the street's interactive props such as doors and breakable fences) and sprites are drawn as before. Older saved edits in the "carrier" format are migrated by dropping their Stage 1 map bytes.

## ROM addressing

`prog.bin` has 0x80000 bytes. Banked CPU addresses 0x6000–0x7fff map to `bank * 0x2000 + address - 0x6000`. Fixed CPU addresses 0x8000–0xffff map to `0x78000 + address - 0x8000`. Words below are big-endian.

The live game stores its scene at RAM offset 0x803, its stage value at 0x875, and section at 0x876. The stage value's high bit selects the four-player tables. `SIMPSTAGE.SCENES` records the twelve editable scene entries and observed palette loads. Other scene numbers are transitions rather than distinct editable backgrounds.

## Map and block tables

The two layer descriptors are at fixed CPU addresses 0xeca1 and 0xecb3, referenced by 0xec9d. Each descriptor's word at +0x10 points to a table indexed by twice the stage index (`stage & 0x7f`). An entry points to section descriptors, four bytes each: a two-byte pointer, bank byte, and unused byte.

A map descriptor points to a list of screen pointers in its bank. Each screen spans eight 32-pixel blocks horizontally, or 256 pixels. Screen data consists of rows of eight two-byte map words. The low ten bits select a block; the editor preserves the other six bits, whose meaning is unverified. The current parser infers screen count from the first screen pointer and row count from the smallest distance between distinct screen pointers, with an eight-row fallback. Section count is inferred from adjacent descriptor lists. These are format assumptions for this ROM set, rather than explicit dimensions stored in an editor file.

Four-player block-table indices are at 0xed29 and 0xedbb. Their section descriptors use the same pointer/bank layout. A block occupies 18 bytes: one K052109 attribute byte, one unused byte, then sixteen tile-code bytes in a 4×4 grid. Each tile is 8×8 pixels. The editor offers block numbers observed in maps using that block table.

Character-bank pairs are read from the stage/section table at 0xef63. `tileNumber()` in `web/stage/stagedata.js` uses the same attribute and bank mapping as `web/sim/video.js`. Palette list tables are at 0xeaeb (four-player) and 0xe9cb (standard). Scene palette IDs and masks were observed at the running game's loader at 0xbcd1. The editor starts with stage 1's palette and overlays the selected scene's palette list.

## Applying edits

The game's startup RAM test writes FF, AA, and 55 through the main-state byte at CPU address 0x4802. Those writes do not indicate successful boot. `web/stage/mods.js` waits for that byte to change from 0 to 1 after the ROM checks, then applies the patch to a private program image. Applying edits earlier fails the game's ROM checksum and prevents normal startup.

Scene selection intercepts the first real-player-game write changing CPU address 0x4803 from 1 to 2 and substitutes the selected scene number. The main mode at RAM offset 0x800 must be 2. Attract mode also uses a 1→2 scene transition and must not consume the selection. The substitution runs once. This is an offline testing aid, not a replacement for the game's stage progression.

## Checks

`node test/stage_check.js` checks patch validation, boot timing, scene selection, and online isolation without a ROM. `python test/test_stage_editor.py` needs the local `roms/simpsons.zip`, Playwright, and Chromium. It checks painting, undo/redo, invalid preferences/imports, online guards, and starting the modified game in stage 2. Screenshots are written under gitignored `preview/`.

`python test/test_enemy_editor.py` checks enemy placement, movement, deletion, history, persistence and import/export. `node test/enemy_check.js` needs the ROM and `unzip` on PATH; it checks all twelve spawn tables, custom sprite data, script order, intact ROM bytes and visible Duffman pixels in a running game.
